# Ключевые решения и договорённости

Не переисследовать заново — сверяться с этим файлом перед изменениями в соответствующих областях.

## Структура репозитория
- `backend/` — .NET решение (`Store.slnx`), `src/` — 4 проекта слоистой архитектуры, `tests/` — юнит-тесты.
- `frontend/` — React/Vite приложение (появится на этапе 5).
- `docs/` — этот прогресс-трекер и решения (не часть ТЗ, только для ускорения работы).
- Git-репозиторий уже существовал на GitHub (`art-mrx/BeruTUT`) с одним коммитом (README). Локальный `git init` + `git merge --allow-unrelated-histories` объединил историю.

## SDK / версии
- Установлены .NET SDK 8/9/10 одновременно. `dotnet new` на SDK 8.0.418 падал с `FileNotFoundException` в template engine (похоже, битая установка) — решили не чинить, а таргетировать `net8.0` через `-f net8.0` на SDK 10 (мультитаргетинг работает нормально). `global.json` НЕ используется.
- Все EF Core / ASP.NET пакеты явно пиннятся на `8.0.11` (последний стабильный 8.x на момент старта), иначе `dotnet add package` без версии подтягивает 10.x, несовместимый с `net8.0`.
- MediatR 12.4.1, AutoMapper 13.0.1 — последние версии до перехода на платную лицензию (более новые мажорные версии — коммерческие, не брать не глядя).
- Solution-файл в новом XML-формате `.slnx` (дефолт для `dotnet new sln` на SDK 10) — это нормально, открывается в VS/Rider/CLI.

## Auth
- Выбран **кастомный JWT** (не ASP.NET Core Identity) — решение пользователя.
- **Доступ к данным из Application-слоя**: вместо generic `IRepository<T>` (как буквально предлагал ТЗ п.3) сделан `IApplicationDbContext` (Store.Application/Common/Interfaces) с `DbSet<T>` — реализует `StoreDbContext`. Это стандартный паттерн для связки CQRS+MediatR+EF Core (Jason Taylor Clean Architecture template) — EF Core `DbSet` уже даёт repository+unit-of-work, обёртка над ним поверх лишняя. Application-проект из-за этого зависит от пакета `Microsoft.EntityFrameworkCore` (только ради типа `DbSet<T>`, без провайдера БД) — это нормально и намеренно.
- **Refresh-токены — senior-подход**: таблица `RefreshTokens` в БД, хранится НЕ сырой токен, а его SHA-256 хеш (`TokenHash`, уникальный индекс). Сырой токен — 64 случайных байта (`RandomNumberGenerator`), отдаётся клиенту один раз.
  - **Ротация**: при каждом `/api/auth/refresh` старый токен помечается `RevokedAt`, выдаётся новый (тот же как OAuth refresh token rotation).
  - **Reuse-detection**: если пришёл токен, у которого `RevokedAt` уже проставлен (т.е. его уже использовали или отозвали) — считаем это признаком кражи и отзываем ВСЕ активные refresh-токены пользователя, требуем перелогин. Из-за этого logout тоже отдаёт "reuse detected" при повторном рефреше уже разлогиненной сессии — это нормально и безопасно (не различаем "украли" от "разлогинились", в обоих случаях доступ закрыт).
  - Пароли — `Microsoft.AspNetCore.Identity.PasswordHasher<User>` (пакет `Microsoft.Extensions.Identity.Core`, НЕ полный Identity — только алгоритм хеширования, PBKDF2). Это то, что подразумевало ТЗ п.6 ("BCrypt/Identity hasher").
  - JWT signing key сгенерирован (64 случайных байта, base64) и лежит в `dotnet user-secrets` проекта Store.Api (НЕ в git). Локально уже настроено — если БД/секреты потеряются на новой машине, надо заново: `dotnet user-secrets set "Jwt:SigningKey" "<base64>"` внутри `backend/src/Store.Api`.
- **`POST /api/auth/logout`** добавлен сверх списка эндпоинтов из ТЗ п.5 — раз завели БД-backed refresh-токены с возможностью отзыва, endpoint для явного отзыва напрашивался сам собой.
- **Единая обработка ошибок** (ТЗ п.6) реализована уже на этом этапе, не отложена на "Полировку" (этап 10) — `Store.Api/Middleware/ExceptionHandlingMiddleware.cs` мапит кастомные исключения (`Store.Application.Common.Exceptions.*`) в ProblemDetails: `ValidationException`→400, `AuthenticationException`→401, `NotFoundException`→404, `ConflictException`→409, всё остальное→500 (с логом полного стектрейса через Serilog, наружу — только общее сообщение).
- FluentValidation подключен через `ValidationBehavior` — MediatR pipeline behavior, все валидаторы гоняются автоматически перед хендлером, ничего вручную вызывать не надо.
- Namespace-ловушка C#: папка/namespace команды `RefreshToken` конфликтовала с именем сущности `Store.Domain.Entities.RefreshToken` (компилятор ищет вложенные namespace'ы раньше using-алиасов) — решено переименованием в `Commands/RefreshTokens` (множественное число). Если заводите новую команду/namespace с именем, совпадающим с именем сущности — сразу называйте во множественном числе, чтобы не наступить на то же самое.

## Локальная БД
- Docker на устройстве пользователя пока не работает — используем локально установленный **PostgreSQL 18** (служба `postgresql-x64-18` в Windows), НЕ контейнер.
- Роль/БД для разработки: `store` / `store` (пароль), БД `store`. Создаются скриптом `backend/scripts/setup-local-db.sql` — **пользователь запускает сам** (там его пароль от суперпользователя `postgres`, Claude пароли не вводит).
- Connection string лежит в `backend/src/Store.Api/appsettings.json` (`ConnectionStrings:DefaultConnection`) — это dev-заглушка с несекретным локальным паролем, для прод/реальных секретов при деплое переходим на env vars / User Secrets (см. ТЗ п.6).
- Docker + docker-compose добавим позже (пользователь хочет подключить, когда почините Docker на устройстве) — Dockerfile/compose файлы можно написать заранее, не запуская.

## Categories + Products
- Поиск по товарам (`search`) сделан через `p.Name.ToLower().Contains(term)` (а не Npgsql-специфичный `EF.Functions.ILike`) — чтобы Application-слой не тянул зависимость на конкретного провайдера БД (Npgsql), которая должна жить только в Infrastructure. Небольшая цена — не использует GIN/trigram индекс, для MVP-масштаба не важно.
- Списки используют `AutoMapper.ProjectTo<T>()` (не `.Map()` после загрузки сущностей) — проекция сразу в SQL, без лишних колонок/N+1.
- `DELETE /api/products/{id}` — это **деактивация** (`IsActive=false`), не удаление строки (см. ТЗ "удалить/деактивировать"), чтобы не ломать FK из OrderItem/CartItem при будущих заказах.
- `DELETE /api/categories/{id}` — жёсткое удаление, но с явной проверкой в хендлере: если есть товары или подкатегории — 409 Conflict с понятным сообщением (а не сырая ошибка БД от FK `Restrict`).
- **Загрузка изображений**: `IFileStorageService` (Application) → `LocalFileStorageService` (Infrastructure) сохраняет файлы на диск в `Store.Api/wwwroot/uploads/products/`, раздаётся через `app.UseStaticFiles()`. Это временное dev-решение — когда дойдём до деплоя, заменить на реализацию поверх S3/Cloudinary/Azure Blob и подменить только DI-регистрацию (интерфейс в Application не поменяется). Сами файлы — в `.gitignore` (папка с `.gitkeep`, чтобы структура была в репо).
- **Admin-пользователь для тестирования**: `Store.Infrastructure/Persistence/Seed/DbSeeder.cs` создаёт одного Admin-пользователя при старте в Development, если Admin ещё нет. Email/FullName — в `appsettings.json` (`AdminSeed:Email`/`FullName`, не секрет), пароль — только в `dotnet user-secrets` (`AdminSeed:Password`); если секрет не задан, сидинг просто пропускается с warning в логах. Текущий пароль пользователю продиктован в чате при создании — если потерян, сгенерировать новый: `dotnet user-secrets set "AdminSeed:Password" "<новый>" --project src/Store.Api`, удалить admin-строку из таблицы `Users` и перезапустить API.
- В локальной dev-БД сейчас лежат тестовые категория "Electronics" и товары "USB Cable"/"Gaming Laptop" (созданы при smoke-тесте) — оставлены специально как образец данных для будущей разработки фронтенда, не нужно удалять.

## Cart + Orders
- Namespace-ловушка (та же, что с `RefreshToken` в Auth) снова всплыла: папка фичи называется `Features/Carts` (множественное число), а не `Cart`, чтобы не конфликтовать с сущностью `Store.Domain.Entities.Cart`. Общее правило зафиксировано — см. запись про Auth выше.
- **Cart vs Order — где хранится цена**: `CartItem` цену не хранит — при отображении корзины цена берётся живьём из `Product.Price` (через AutoMapper `MapFrom`). `OrderItem` — наоборот, хранит `ProductName`/`Price` как снапшот на момент оформления заказа (так и было заложено в доменной модели ещё на этапе 1). Это осознанно: корзина показывает актуальную цену, заказ — историю по факту покупки, даже если товар потом подорожает/переименуется/удалится.
- **Проверка остатков — два уровня**: мягкая проверка при добавлении/изменении позиции в корзине (`AddCartItemCommandHandler`/`UpdateCartItemCommandHandler`, 409 при превышении) и повторная авторитетная проверка при оформлении заказа (`CreateOrderCommandHandler`) — между добавлением в корзину и чекаутом остаток мог измениться (кто-то другой купил последний). Чекаут никогда не доверяет более ранним проверкам.
- **Гонки/конкурентность**: сейчас нет optimistic concurrency token на `Product.StockQuantity` — при одновременных заказах на последнюю единицу теоретически возможен race condition (оба запроса проходят проверку, оба списывают остаток в минус). Для пет-проекта это сознательно не реализовано (не было в ТЗ), но если понадобится — добавить `[ConcurrencyCheck]`/`RowVersion` на `Product` и обрабатывать `DbUpdateConcurrencyException` в `CreateOrderCommandHandler`.
- **Тесты бизнес-логики** (ТЗ п.9, `tests/Store.Application.Tests`): решили тестировать реальные MediatR-хендлеры (`CreateOrderCommandHandler`, `AddCartItemCommandHandler`) через **EF Core InMemory provider**, а не через моки `IApplicationDbContext`/`DbSet` — мокать LINQ-запросы поверх `DbSet<T>` в Moq болезненно и хрупко; InMemory даёт реальное поведение EF Core (Include, LINQ-трансляция) почти бесплатно. `IMapper` в тестах — настоящий (собран из всех профилей сборки), не мок — заодно ловит ошибки конфигурации маппинга (см. `MapperProfilesTests`).
- **Баг с enum в JSON-теле**: `System.Text.Json` по умолчанию не умеет `"status":"Processing"` → `OrderStatus` (ждёт число). Пофикшено глобально через `AddJsonOptions(o => o.JsonSerializerOptions.Converters.Add(new JsonStringEnumConverter()))` в `Program.cs`. Если будут другие enum-поля в теле запроса (не query-параметры — те и так работали через стандартный model binding) — этот конвертер их тоже покроет.
- `PUT /api/admin/orders/{id}/status` не имеет state-machine валидации переходов (например, из `Delivered` обратно в `New`) — намеренно, ТЗ этого не требует, это MVP-simplification.

## Frontend skeleton
- **React 18, не React 19**: скаффолд `npm create vite@latest` по умолчанию поставил React 19 — откатили на `^18.3.1` (+ `@types/react` 18.x), т.к. ТЗ п.2 явно фиксирует React 18.
- **React Router v7, не v6**: ТЗ фиксирует v6, но `react-router-dom` версий 6.0.0–7.17.0 имеет две модерейт CVE (open redirect через backslash в `<Link>`/`useNavigate`; arbitrary constructor injection в SSR-гидратации). Патч есть только в 7.18+. Осознанно отклонились от ТЗ в пользу безопасности — поставили `react-router-dom@latest` (7.x). API роутинга (`createBrowserRouter`, `RouterProvider`, `Outlet`) не поменялось между v6.4+ и v7, так что архитектурно это не расхождение, только версия пакета.
- **Tailwind v4** (не v3 из ТЗ, версия там не была явно зафиксирована) — подключается через `@tailwindcss/vite`, без отдельного `tailwind.config.js`/PostCSS (новый механизм v4), директива `@import "tailwindcss";` в `index.css`.
- **Путь-алиас `@/*` → `src/*`**: настроен в обоих местах — `vite.config.ts` (`resolve.alias`, через `import.meta.dirname`, НЕ `__dirname` — новый native config loader Vite это не поддерживает) и `tsconfig.app.json` (`compilerOptions.paths`, без `baseUrl` — в TS ~6.0 с `moduleResolution: "bundler"` он не нужен и вообще deprecated).
- **API-клиент и refresh-токены**: `src/api/client.ts` — axios-инстанс с request-интерцептором (подстановка access token из Zustand-стора) и response-интерцептором на 401. Важный нюанс: backend ротирует refresh-токен на каждый `/auth/refresh` и считает повторное предъявление уже использованного токена кражей — отзывает ВСЕ сессии пользователя (см. Auth-раздел выше). Поэтому при параллельных 401 от нескольких запросов интерцептор обязан вызвать `/auth/refresh` только один раз (single-flight через общий `refreshPromise`), а не по разу на каждый упавший запрос — иначе второй вызов рефреша словит "reuse detected" и разлогинит пользователя.
- **Хранение токенов**: Zustand-стор (`features/auth/authStore.ts`) с `persist` в `localStorage`. Это осознанный компромисс для SPA без отдельного BFF/httpOnly-cookie слоя — токены теоретически доступны через XSS. Раз ТЗ не просит cookie-based flow и backend отдаёт токены в теле JSON-ответа (не Set-Cookie), альтернативы без переделки backend нет. Если проект пойдёт дальше MVP — рассмотреть httpOnly cookie + BFF.
- **Типы `src/types/*` — camelCase**: ASP.NET Core по умолчанию сериализует JSON в camelCase, поэтому TS-типы списаны с реальных ответов API напрямую (не PascalCase из C#).
- **`routes/router.tsx`**: все маршруты из ТЗ п.7 (включая `/admin/*`, `/checkout`, `/orders/:id`) заведены сразу на этапе 5 со страницами-заглушками ("появится на этапе N") — чтобы `ProtectedRoute`/`AdminRoute` и общая структура роутинга были на месте, а этапы 6-9 просто наполняли уже существующие файлы страниц реальным содержимым, не трогая роутинг.
- **CORS не настроен** — в деве не нужен благодаря Vite dev-прокси (`vite.config.ts` → `/api`, `/uploads` на `http://localhost:5080`, same-origin с точки зрения браузера). Понадобится при деплое, когда frontend и backend окажутся на разных доменах — добавить на этапе 10 или при настройке хостинга, когда будет известен реальный домен фронтенда (ТЗ п.6).
- Node.js добавлен в PATH через `winget`, но уже запущенные терминалы/процессы (включая эту сессию) PATH не подхватывают — путь к `node`/`npm` пришлось прописывать явно (`C:\Program Files\nodejs\...`) в `.claude/launch.json` и командах. В новых терминалах после установки `node`/`npm` работают из коробки.

## Каталог (frontend)
- **Несостыковка ТЗ↔backend обнаружена и исправлена**: ТЗ п.7 фиксирует маршрут `/products/:slug`, но backend с этапа 3 умел искать товар только по `Guid id` (`GET /api/products/{id:guid}`). Исправлено на backend: `GetProductByIdQuery.IdOrSlug` (string) — хендлер сначала пробует распарсить как Guid, если не вышло — ищет по `Slug`. Роут в `ProductsController` стал `{idOrSlug}` без constraint. Admin-эндпоинты (Update/Delete/UploadImage) по-прежнему принимают только `{id:guid}` — им нужен именно Guid, слаг там не нужен.
- **Фильтры каталога — состояние в URL** (`useSearchParams`), не в локальном стейте компонента — так фильтры переживают back/forward браузера и страницу можно кидать ссылкой с уже применённым фильтром. Стандартный паттерн для каталогов.
- **Debounce на поиске и цене** (`hooks/useDebouncedValue.ts`, 300мс) — иначе каждое нажатие клавиши слало бы новый запрос к `/api/products`.
- **`placeholderData` вместо `keepPreviousData`** в `useProducts` — TanStack Query v5 переименовал API пагинации без "прыжка" контента при смене страницы.
- **Валюта в UI — USD** (`src/lib/format.ts`, `Intl.NumberFormat('en-US', {currency:'USD'})`): ТЗ не фиксирует валюту, цены в сид-данных (`$5.99`, `$1999.99`) уже были выбраны в долларовом масштабе на этапе 3 — просто продолжили это соглашение. Легко поменять в одном месте, если понадобится другая валюта/локаль.
- Товар без изображений — обычное дело в MVP (загрузка картинок делает Admin вручную через `/products/{id}/images`), поэтому и `ProductCard`, и `ProductDetailPage` рассчитаны на `imageUrls: []` (плейсхолдер "Нет фото"), это не баг.
- Кнопку "добавить в корзину" на карточке товара сознательно не завели — по плану ТЗ п.8 корзина на фронте — отдельный этап 8, чтобы не размывать границы этапов.

## Auth (frontend)
- **Поле "подтвердите пароль"** на регистрации — есть только на клиенте (Zod `.refine`), backend его не знает и не ждёт (`RegisterCommand` принимает только `password`). Обычная UX-практика, не расхождение с API.
- **Обработка ошибок форм**: `lib/apiError.ts` различает два случая ответа backend (см. `ExceptionHandlingMiddleware` в backend/docs) — `ProblemDetails.errors` (400 от FluentValidation, ключи PascalCase типа `"Email"`) мапится на конкретные поля формы через `setError` (с приведением первой буквы к нижнему регистру под camelCase-имена полей формы); всё остальное (401 неверный пароль, 409 дубликат email — там `errors` нет, только `detail`) показывается общим баннером над кнопкой submit.
- **Редирект после логина**: `ProtectedRoute` (этап 5) кладёт `location` в `state.from` при редиректе на `/login`; `LoginPage` после успешного логина уводит обратно туда же (`navigate(from)`), а не всегда на `/`. Уже залогиненного пользователя со страниц `/login`/`/register` уводит на `/` (или на `from`, если есть) — стандартный UX-паттерн, чтобы нельзя было руками открыть форму логина будучи уже авторизованным.
- Мутации логина/регистрации намеренно НЕ инвалидируют/не рефетчат React Query кэш каталога и т.п. — `setAuth` просто кладёт токены/пользователя в Zustand, дальнейшие запросы сами подхватят новый access token через axios-интерцептор (см. этап 5).

## Корзина и чекаут (frontend)
- **Роутинг-баг найден и исправлен**: `/cart` был заведён на этапе 5 как публичный маршрут (наравне с `/login`), хотя `CartController` на backend требует `[Authorize]` с самого этапа 4. Перенесён под `ProtectedRoute` в `router.tsx`.
- **Нет отдельного Zustand-стора корзины**, хотя структура ТЗ п.7 подразумевает `features/cart/ — корзина, стор корзины`. Корзина в нашей модели существует только у авторизованного пользователя (backend не поддерживает гостевую корзину — `Cart.UserId`, `CartController` требует токен), так что дублировать серверное состояние в отдельном клиентском сторе не имеет смысла — источник истины один: React Query кэш по ключу `['cart']`. Мутации (`useAddCartItem`/`useUpdateCartItem`) сами кладут обновлённый `CartDto` в кэш через `setQueryData` (ответ backend уже содержит актуальную корзину), без похода за новым GET.
- **Кнопка "+" в корзине не ограничена известным остатком** (в отличие от карточки товара, где `Math.min(product.stockQuantity, ...)` — там остаток известен из `ProductDto`). `CartItemDto` не содержит `stockQuantity`, так что при превышении backend просто вернёт 409 — ошибка показывается прямо в строке товара (`CartItemRow`), количество не меняется. Сознательно не стали гонять лишний `GET /api/products/{id}` на каждый клик ради UI-подсказки лимита — MVP-компромисс.
- **"Добавлено в корзину" на карточке товара** — состояние успеха мутации (`addCartItem.isSuccess`), держится до следующего действия пользователя, авто-скрытия по таймеру нет — простое решение для MVP.

## Админка (frontend)
- **Backend-пробел найден и закрыт**: публичный `GET /api/products` всегда фильтрует `IsActive=true` (осознанно, этап 3). Но это означает, что деактивированный товар исчезал из ЛЮБОГО способа его увидеть — включая саму админку, которая должна уметь его найти и вернуть в продажу. Решение — `GET /api/admin/products` (`AdminProductsController`, Admin-only), переиспользует `GetProductsQuery`/хендлер/все фильтры-сортировки-пагинацию публичного эндпоинта, просто форсит `IncludeInactive = true`. Тот же паттерн, что уже был у Orders (`/api/orders` vs `/api/admin/orders`) — не новая архитектура, а достройка существующей.
- **CRUD-формы без модалок**: форма создания/редактирования — инлайн-панель над таблицей (тот же `<form>` переиспользуется для create и update через `editing: T | null` в стейте), не отдельный компонент-модалка. Меньше кода для MVP-админки, стандартный паттерн для простых CRUD-таблиц.
- **`window.confirm` перед удалением** — самое простое решение без раздутия скоупа отдельным confirm-диалогом/тостами. Минус: в автоматизированных браузерах (в т.ч. при моём собственном smoke-тесте) `confirm()` по умолчанию отклоняется — учитывайте это, если пишете e2e-тесты на эту админку.
- **"Скрыть" на товаре = DELETE, "Показать" = PUT с `isActive:true`** — раздельная логика, т.к. на backend нет отдельного "activate"-эндпоинта: DELETE только деактивирует (см. `DeleteProductCommandHandler`), обратного пути там нет. `toggleActive()` в `AdminProductsPage` явно ветвится на это.
- **`ProductPayload` (create) больше не содержит `isActive`** — на создании товар всегда активен (backend `CreateProductCommandHandler` жёстко ставит `IsActive = true`, поле в команде отсутствует). Оставлен отдельный `ProductUpdatePayload extends ProductPayload { isActive: boolean }` для update — обязательное поле, не опциональное, потому что `UpdateProductCommand.IsActive` на backend — обязательный `bool` (не `bool?`), и пропуск поля в JSON тихо десериализуется в `false`, деактивируя товар при любом безобидном редактировании. Наступить на эти грабли один раз и задокументировать оказалось дешевле, чем ловить баг в проде.

## Полировка (этап 10)
- **CORS**: `builder.Services.AddCors` + `Cors:AllowedOrigins` в конфиге (массив строк), а не хардкод в коде — прод-домен фронтенда узнаем только на деплое, добавить туда же (`appsettings.Production.json` или env var `Cors__AllowedOrigins__0`). Dev-значение (`http://localhost:5173`) лежит в `appsettings.Development.json`. До этого этапа CORS не был нужен — Vite dev-прокси делает запросы same-origin с точки зрения браузера (см. этап 5), но при реальном деплое на разные домены (Vercel/Render) без CORS браузер заблокирует все запросы с фронтенда.
- **Адаптивность — реальный баг найден вручную через resize_window('mobile')**: строка корзины (`CartItemRow.tsx`) на 375px обрезала кнопку "Удалить" за пределами экрана (DOM-элемент существовал, но визуально был недоступен — `get_page_text` показывал текст, `screenshot` — нет). Причина: `flex items-center` без `flex-wrap` на строке с шестью элементами фиксированной ширины. Исправлено группировкой qty-контролов/суммы/кнопки в отдельный `ml-auto flex flex-wrap` блок, который целиком переносится на новую строку под названием товара, если не помещается.
- **Admin-таблицы** (`AdminProductsPage`/`AdminOrdersPage`/`AdminCategoriesPage`) обёрнуты в `<div className="overflow-x-auto">` с `min-w-[...]` на самой таблице — на мобильном таблица скроллится горизонтально внутри своего контейнера, не растягивая всю страницу и не ломая остальной layout.
- **`ErrorBoundary`** — простой class-компонент (только он поддерживает `componentDidCatch`/`getDerivedStateFromError`, hooks-эквивалента в React 18 нет), оборачивает всё приложение в `main.tsx` снаружи `QueryClientProvider`/`RouterProvider`. Ловит только ошибки рендера/lifecycle, не ошибки в event-хендлерах или async-коде (те и так обрабатываются через React Query `isError`/`onError` по всему приложению) — это осознанное разделение ответственности, не пробел.
- **Деплой не выполнен** — README описывает план (Railway/Render/Vercel/Neon по ТЗ п.2), но сам деплой требует аккаунтов пользователя на этих сервисах и решений (какой именно хостинг, платный/бесплатный тир и т.д.), которые не должны приниматься за пользователя молча.

## Грабли: user-secrets, заданные из окружения Claude, невидимы в обычном терминале
- Команды `dotnet user-secrets set ...`, выполненные через инструменты Claude (десктопное приложение — MSIX/Store-пакет), пишут в **виртуализированный** `%APPDATA%` (`C:\Users\<user>\AppData\Local\Packages\Claude_*\LocalCache\Roaming\Microsoft\UserSecrets\<id>`), а не в настоящий. Обычный PowerShell/IDE пользователя читает настоящий `%APPDATA%` и секретов не видит.
- Симптом: backend, запущенный самим пользователем, отвечает `500 An unexpected error occurred` на любой запрос с аутентификацией (`ArgumentNullException ... Encoding.GetBytes` в `Program.cs` на `jwtSettings.SigningKey`), при том что у Claude тот же код и та же БД работают. В логе консоли — стек с `Program.cs:54`.
- Решение: секреты (`Jwt:SigningKey`, при необходимости `AdminSeed:Password`) пользователь задаёт **сам в своём терминале** (см. README, шаг Backend). Хранить их в репозитории по-прежнему нельзя. Аккаунты и пароли в БД не затрагиваются — они лежат в Postgres, а не в секретах.
- Побочно: чужие `dotnet user-secrets list` из Claude-окружения покажут значения, которых нет в обычной оболочке — не путаться.

## Подтверждение заказов админом
- **Остаток резервируется при оформлении, а не при подтверждении.** Так уже было с этапа 4 (списание в `CreateOrderCommandHandler`). Это соответствует сценарию «клиент заказал → с ним созваниваются»: пока админ не позвонил, товар не должен продаться второму клиенту. Подтверждение остаток не трогает, отклонение возвращает. Альтернатива (списывать при подтверждении) допускала бы продажу одного товара двум клиентам до звонка.
- **Почему пришлось ввести правила переходов, а не только две кнопки.** Раньше `PUT /api/admin/orders/{id}/status` менял статус на любой (осознанное упрощение этапа 4). С возвратом остатка это стало бы багом: можно «отклонить» дважды и получить остаток вдвое больше, либо вернуть отклонённый в «новый» без повторного резерва. Поэтому `OrderStatusRules` (Domain) — единственный источник допустимых переходов, `Cancelled` и `Delivered` конечные.
- **Отдельных эндпоинтов approve/reject нет** — подтверждение/отклонение это `PUT .../status` со значением `Approved`/`Cancelled`. Меньше API-поверхности, вся логика в одном хендлере.
- **Имя `Cancelled` оставлено** (как в ТЗ п.4 и в существующих данных), в интерфейсе показывается «Отклонён» (`features/orders/statusLabels.ts`). Переименование в `Rejected` потребовало бы менять контракт API и ТЗ ради косметики. `Approved` добавлен в конец enum со значением 5: статус хранится числом, перенумеровывать нельзя.
- **`AllowedNextStatuses` в `AdminOrderDto`** — вычисляемое get-only свойство. AutoMapper считает get-only коллекции немаппленными и роняет `AssertConfigurationIsValid` (это поймал `MapperProfilesTests`), поэтому в `OrderMappingProfile` оно явно `Ignore()`.
- **Телефон — на заказе, а не на пользователе** (`Order.ContactPhone`): снапшот на момент заказа, как и адрес, клиент может указать другой номер под конкретный заказ. Допущение: в исходной модели телефона не было, а «созваниваются» его подразумевает.
- **Админка: `AdminLayout` с вкладками.** До этого админские страницы не были связаны между собой навигацией вообще. Счётчик «Ожидают подтверждения» опрашивается раз в 30 сек (`refetchInterval`) — без WebSocket/SignalR, для MVP достаточно. Очередь показывается от новых к старым; для очереди звонков «сначала старые» был бы логичнее — не сделано, при необходимости добавить сортировку в `GetAdminOrdersQuery`.
- **Фильтры списка заказов — как устроены.**
  - «Номер заказа» — это первые 8 символов `Order.Id` (то, что показано как «№ 1a15acc7»); отдельного порядкового номера в модели нет. Поиск — подстрока `Id::text` без учёта регистра, терпит «№»/«#». Search по имени/email/телефону клиента не делали (просили только номер) — при необходимости добавить в тот же `GetAdminOrdersQueryHandler`.
  - **Даты передаются как UTC-диапазон `[createdFrom, createdTo)`** — `createdTo` НЕ включительно. `<input type="date">` даёт локальный день админа; `lib/dates.ts` переводит его в границы *локальных* суток (`startOfLocalDayIso` / начало следующего дня), поэтому «16.09» в любом часовом поясе означает именно календарный день админа, а не UTC-сутки. Backend приводит `Kind=Unspecified` к UTC (Npgsql для `timestamptz` принимает только `Utc`, иначе исключение).
  - Сортировка по `CreatedAt` + `Id` вторым ключом — стабильная пагинация при одинаковых временах.
  - Любое изменение фильтра сбрасывает страницу на 1 (иначе текущей страницы может не быть в новой выборке). Некорректный диапазон (`с` > `по`) на клиенте не отправляется — показывается подсказка; backend тоже отвечает 400.
  - InMemory-тесты не доказывают трансляцию `Id.ToString().Contains(...)` в SQL Npgsql — поэтому поиск отдельно проверен на настоящей БД.
- **Как проверять backend-изменения, не останавливая dev-сервер пользователя:** `dotnet build src/Store.Api/Store.Api.csproj -o <отдельный каталог>` и запуск оттуда на другом порту (`dotnet Store.Api.dll --urls http://localhost:5081`); для фронтенда — второй `vite` на другом порту с `API_PROXY_TARGET=http://localhost:5081` (переменная поддерживается в `vite.config.ts`, по умолчанию `:5080`). Миграции так не применить — для `dotnet ef` backend остановить.
- **Грабли: dev-сервер backend блокирует сборку.** Запущенный `Store.Api.exe` держит DLL, `dotnet build`/`dotnet ef` падают с MSB3027. Перед сборкой и миграциями backend надо остановить (`Ctrl+C`).
